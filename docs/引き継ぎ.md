## 1. 新セッションが最初に知るべきこと（重要・つまずき防止）

1. **これは“いつものNext.js”ではない**：**Next.js 16**（App Router / Turbopack）。APIが学習データと異なる場合がある。
   コードを書く前に `node_modules/next/dist/docs/` の該当ガイドを読む（`AGENTS.md` の指示）。
2. **Bashサンドボックスがネットワークを遮断している**：`npm install` / `npm run build`（`next/font`のフォント取得）/ 外部取得は
   **`dangerouslyDisableSandbox: true` を付けて実行**する。付けないと `ENOTFOUND registry.npmjs.org` で失敗する。
3. **シェルは zsh**：`shopt` 等のbash builtinは使えない。必要なら `bash -c '...'` で実行する。
4. **単一情報源（ここだけ直せば全体に反映）**：
   - `src/lib/site.ts` … 社名・URL・NAP・SNS・keywords・knowsAbout
   - `src/lib/content.ts` … 掲載内容（サービス/料金/実績/お客様の声/FAQ/要点/AEO）
   - `src/lib/jsonld.ts` … 構造化データ（JSON-LD）ビルダー
   - `src/app/globals.css` … ブランドカラー・フォント（`@theme`）
5. **`★` 印 = 差し替え必須のプレースホルダ**（`site.ts` 等）。
6. **検証コマンド**（下記5章）でビルド・型・Lint・実機HTMLを必ず確認する。
7. **技術メモ**：Tailwind **v4**（`@theme`／CSS変数）。`"use server"` ファイルは**async関数しかexport不可**
   （型・定数は別ファイルへ。例：`src/app/contact-state.ts`）。OG画像のsatori既定フォントは**日本語非対応**（画像内はラテン文字主体）。

- ✅ **日本語の組版（語中改行）を全ページで修正／見出し文言の刷新（2026-08-02）**
  - **問題**：ブラウザは日本語をどの文字間でも折り返すため、「チャット／ボット」「シミュレー／ター」のように
    カタカナ語が途中で割れていた（実測：8ページ × 3画面幅で 87 箇所）。
  - **対策1（組版）**：`src/lib/typography.tsx` の `ja(text)` が、カタカナの連なりと
    記号入り英数字（Wi-Fi / N-gram / llms.txt）を `<span class="nb">` `<span class="nb-strict">` で包む。
    CSSは `globals.css`（`.nb` は `word-break: keep-all` ＋ 収まらないときだけ `overflow-wrap: break-word`、
    `.nb-strict` は `display:inline-block; white-space:nowrap`）。
    **文字は一切足していない**（U+2060 等を挟んでいない）ので、コピー・読み上げ・SEO・JSON-LD に影響しない。
    見出しなど JSX を受け取る共通部品では `jaNode()`（文字列だけ処理）を使う。
  - **対策2（Chromeのみ）**：`@supports (word-break: auto-phrase)` で文節折り返しを有効化。
    「つくり／ます」のような切れ方が減る。Safari / Firefox は未対応だが、対策1で語割れは防げている。
  - ⚠️ **落とし穴**：折り返し禁止の語を含む行は、Chromeが**flex項目の最小幅（min-content）を過大に見積もる**。
    その結果カードがグリッドのトラック幅を超え、320px幅で横スクロールが出た。

### ページ内メニューの現在地判定（2026-08-03 に作り直し）

`src/components/fx/useSectionSpy.ts` に集約（`site/PageNav` と `fx/SectionNav` が共用）。

- 判定は**面積比を使わない**。IntersectionObserver の `intersectionRatio` はセクション自身の
  高さに対する比なので、背の低い節ほど有利になり、画面の高さ次第で「1つ前の節」が光っていた
  （例：トップで「事業内容」を押すと「30秒でわかる」に戻る）。
- 現在地＝**アンカーで移動したときに止まる線を、最後に越えたセクション**。
  その線は `html` の `scroll-padding-top` と各セクションの `scroll-margin-top` の**合計**
  （現状は 80px + 80px = 160px）。移動先と判定基準が同じ線になるので、画面サイズで結果が変わらない。
- 線はスタイルの読み込み待ちや画面幅で変わるため、**キャッシュせず毎フレーム測り直す**。
  マウント時に一度だけ測ると、CSS適用前の値を掴んで判定が1つずれる。
- メニューをクリックした直後は、自動スクロールが終わるまで判定を止める（通過する節でのちらつき防止）。

### 表示速度を守るための鉄則（2026-08-02 追加）

見た目が何も変わらないまま重くなるパターンが実際に起きたので、以下を守ること。

- **`"use client"` のコンポーネントから `content.ts` を import しない。**
  1800行ぶんのコンテンツがまるごと初期JSに載る（実測でgzip換算 約17KB）。
  ヘッダーのように全ページ共通かつクライアント側で使うデータは `src/lib/nav.ts` に置く。
- **職種データ（`showcaseData.ts`）をクライアントから import しない。** `content.ts` と同じ理由。
  型と定数は `showcase.ts` に分けてある。1職種ぶんはサーバーから props で渡すこと。
- **`next/link` には `prefetch={false}` を付ける。** 付けないと画面内に入っただけで
  リンク先のRSCペイロード（1ページ60〜140KB）を先読みする。トップは本文だけで15本あり、
  スクロールしただけで800KB超を取得していた。ホバー時の先読みはNext.js側に残るため遷移は速いまま。
- **`backdrop-filter`（すりガラス）を、動く背景の上に重ねない。**
  3D背景・オーロラが動いているとぼかし結果をキャッシュできず、スクロール中ずっと再合成が走る。
  ヘッダーはこれが理由で不透明背景に変更済み。`.panel`（1ページに27枚）にはまだ残っている。
- 変更後は `npm run build:pages && npm run size` で数字を確認する。

### 文章を出すときの鉄則（2026-08-02 追加）

- **画面に出す日本語は、JSXに直接書いたものも含めてすべて `ja()` を通す。**
  `{s.description}` ではなく `{ja(s.description)}`、`<strong>制作期間は…</strong>` ではなく
  `<strong>{ja("制作期間は…")}</strong>`。`{siteConfig.name}` のような値の埋め込みも同じ。
  通していないテキストは語の途中で改行される（「従／来」「所／属」「チャット／ボット」）。
  JSXが混ざる見出しなどは `jaNode()`（子要素をたどって中の文字列も処理する）。
  `Button`/`ButtonLink`・`SectionHeading`・`PageHeader` は内部で `jaNode()` 済みなので、
  これらに渡すぶんには不要。JSONLD・llms.txt・metadata には**通さない**（素の文字列のまま使う）。
- **通し漏れの探し方**：ヘッドレスChromeで「日本語を含むのに `span.nb` に包まれていない
  テキストノード」を列挙すると、漏れがそのまま出る。実測が唯一の確認手段。
- **アイコン＋テキストの `li`（flex）では、テキスト側に `min-w-0` を付ける。**
  付けないと折り返し禁止の語がある行でカードが横に膨らむ。
- **`word-break: auto-phrase`（文節での折り返し）は当てにしない（2026-08-03）。**
  `CSS.supports()` は true を返すのに、折り返し位置は何も変わらず、カタカナすら
  「ソフトウェ／ア」と割れることを実測で確認した。**どこで切ってよいかは `ja()`（サーバー側）が決める。**
- **`ja()` は文章を「語のまとまり」に切って `.nb` で包む。** 自立語（漢字・カタカナ・英数字）に
  続くひらがな（送り仮名・助詞）まで1つの塊にするので、「制作期間は」「開発しています」の単位で
  折り返される。ひらがなだけの語も包む（「ください」「いただけます」）。
  上限は全角9文字ぶん（`MAX_WIDTH`）。超えるぶんは次の塊へ送るので、狭い画面でも溢れない。
- **`.nb` を `display: inline-block` にしないこと。** 語を「箱」にすると地の文から切り離され、
  「Webサイト／をつくります」のように助詞だけが次行に落ちる。`white-space: nowrap`（inline のまま）にする。
- **小見出し（h3/h4）に `text-wrap: balance` を使わない（2026-08-03）。** 行の長さを揃えることが
  優先され、「AI機能その／ものを開発している」のように文節を無視した位置で折れる。
  h1/h2 は行数が少なく balance の効果が勝るため、そちらだけ balance のまま。
- 変更後は語中改行と横はみ出しを実測で確認する（ヘッドレスChrome）。

### ⚠️ 狭い画面幅の実測は `--window-size` では測れない（2026-08-03 に一度騙された）

**ヘッドレスChromeのウィンドウ幅は 500px 未満にならない。**
`--window-size=390,800` と指定しても、実際のレンダリングは **500px 幅**で行われ、
`--screenshot` は「500px 幅で描いたページの左390px」を切り出した画像を返す。
そのため**スマホ幅では起きていない見切れが、画像の上では起きているように見える**
（実際にこれで「ハンバーガーが画面外に出ている」と誤診した。本当は正常だった）。

正しい測り方は、**幅を指定した iframe に本番HTMLを読み込み、中の
`documentElement.scrollWidth` と `clientWidth` を比べる**こと。
ウィンドウ幅の制限を受けず、320px でも正確に測れる。

```js
// out/ に一時HTMLを置き、http.server 経由で開く（file:// だと iframe を読めない）
const f = document.getElementById('f');          // <iframe src="/index.html">
f.style.width = '320px';
const d = f.contentDocument;
d.documentElement.scrollWidth > d.documentElement.clientWidth  // true なら横はみ出し
```

`--screenshot` は**見た目の確認にだけ使い、幅の判定には使わないこと**。
判定に使ってよいのは 500px 以上の幅だけ（1024 / 1280 などのヘッダー検証は問題ない）。

## 6. 今後の予定（簡易・公開後）

公開を一旦のゴールとし、その後に着手予定の構想。

- **⚠️ さくら本番の Brotli 圧縮（2026-08-04・WAFを優先し「圧縮なし」で運用決定）**：

  > **結論：WAF を有効のまま運用するため、本番は無圧縮で配信している。**
  > 8/3 に WAF を無効化して圧縮を通したが、8/4 に Search Console のサイトマップが
  > 「取得できませんでした」となり、WAF を再有効化したところ公開URLテストが通った。
  > 因果は確定していない（送信当日は最終読み込み日時が空のまま「取得できませんでした」と
  > 表示されるだけのことも多く、ライブテストで初めて取りに行った可能性もある）が、
  > **クローラに確実に届くことを優先し、WAF ON ＝ 圧縮なしを選択した。**
  > WAF が `Accept-Encoding` を削除するため、`.htaccess` 側では圧縮を復活できない。
  > トップの HTML は非圧縮 約422KB。速度を詰めるなら HTML/JS 自体を削ること。
  >
  > **事前圧縮は既定で作らない（2026-08-05）。** 配信されないファイルを毎回送ると
  > 転送ファイル数が3倍（533 → 1599）になり、FTPS転送が不安定になって
  > `mirror: ... No such file or directory` を大量に出して落ちるようになったため。
  > `npm run build:sakura` は素のビルドのみ。圧縮つきは `build:sakura:br`。
  > **WAFを無効化して圧縮を使う運用に戻すときは `PRECOMPRESS=1 npm run deploy:sakura`**
  > （または `scripts/deploy-sakura.sh` の `PRECOMPRESS` 既定値を 1 にする）。
  >
  > なお `sitemap.xml` と `robots.txt` は、WAF を将来外した場合でも圧縮版に
  > 差し替えられないよう `.htaccess` のリライトから除外してある（クローラ向けの
  > 配信経路を単純に保つため。数KBなので転送量にも影響しない）。
  >
  > **圧縮版のヘッダー自体は正常なことを 8/4 に実測で確認済み**：
  > `sitemap.xml.gz` → `Content-Type: application/xml` ＋ `Content-Encoding: gzip`。
  > 下に書いた `RemoveType .gz` は正しく効いており、x-gzip 問題は再発していない。

  以下は、WAF を無効化していた 2026-08-03 当時の記録：

  > **解決した。** コントロールパネルで WAF（SiteGuard）を無効化した結果、
  > `Accept-Encoding` が Apache まで届くようになり、`.br` / `.gz` の出し分けが本番で動作。
  > レスポンスから `Via: ...guard.sakura.ne.jp` も消えている。
  > トップは `Content-Encoding: br` で配信中（`npm run deploy:sakura` の最後で自動確認）。
  >
  > **ただし `.gz` 側に落とし穴があった（2026-08-03・修正済み）。**
  > さくらの Apache は既定で `AddType application/x-gzip .gz` を持っており、
  > `.br`（未知の拡張子＝型判定で無視される）と違って **`.gz` は型が上書きされる**。
  > その結果、gzip を要求したクライアントには
  > `sitemap.xml` が `Content-Type: application/x-gzip`、
  > トップの HTML までもが `text/html` ではなく `application/x-gzip` で返っていた。
  > **Googlebot は br を送らず gzip を送る**ため、Search Console が
  > 「サイトマップを読み込めませんでした」（検出ページ数 0）になっていた。
  > br でしか確認していないと気づけないので注意。
  >
  > 対処は `public/.htaccess` の mod_mime 節に **`RemoveType .gz`** を1行足すだけ。
  > `.gz` の型定義を消せば `.br` と同じく元の拡張子（`.xml` → `application/xml`）で
  > 型が決まり、`AddEncoding` が encoding だけを足す。
  > 確認コマンド（Googlebot と同じく gzip だけを要求する）：
  >
  > ```sh
  > curl -sI -H 'Accept-Encoding: gzip' https://www.yebisusoft.jp/sitemap.xml \
  >   | grep -i '^content-type\|^content-encoding'
  > # → content-type: application/xml / content-encoding: gzip なら正常
  > ```

  以下は、WAF が有効だった当時の調査記録（同じ症状に出会ったときの参考）：

  > **本番のさくらでは無効。原因は前段のWAF。**
  > レスポンスの `Via: 1.0 ss20xx.guard.sakura.ne.jp (EG Secure Solutions/siteguard_http_01/...)`
  > が示すとおり、さくらは SiteGuard（WAF）を挟んでいる。これが**リクエストの
  > `Accept-Encoding` だけ**を削除しており、Apache に届かない。
  > WAFが本文を検査するために平文を要求する、よくある挙動。
  > そのため `.htaccess` の `RewriteCond %{HTTP:Accept-Encoding}` は常に不成立になり、
  > `.br`/`.gz` は一切選ばれない。**`mod_deflate` が効かなかった原因もこれ**（モジュールの
  > 有無ではなかった）。下記の「検証」はローカルの Apache 単体で行ったもので、
  > さくらの前段WAFを再現できていなかった。
  >
  > 実測での確認（2026-08-03、本番）：
  > - `_hdrprobe.php` を一時的に置いて `$_SERVER` をダンプ → **`HTTP_ACCEPT_ENCODING` だけが存在しない**。
  >   `HTTP_ACCEPT` も独自ヘッダー `X-Test` も届いているので、この1つを狙って落とされている。
  >   HTTP/1.1・HTTP/2、ブラウザUA、いずれでも同じ。（確認後このPHPは削除済み）
  > - 条件なしの `RewriteRule ^_ae-none$ /index.html.br [L]` → **200**（リライト自体は動く）
  > - `RewriteCond %{HTTP:Accept-Encoding} .+` を足すと → **404**（＝ヘッダーが空）
  > - `/index.html.br` を直接叩けば `Content-Encoding: br` で正しく返る（`AddEncoding` は有効）
  > - Chrome（Playwright）で本番を開いた実測：トップの転送量 **1,726KB**、`Content-Encoding: br` は **0件/17件**
  >
  > **次の一手：さくらのコントロールパネルで WAF を無効化する**（手順と確認コマンドは
  > `docs/集客セットアップ.md` 4章。`npm run deploy:sakura` の最後でも圧縮の有無を自動で確認する）。
  > 本サイトは完全な静的配信でPHPもDBも無く、WAFが守る対象がない。
  > 無効化すれば `precompress.mjs` と `.htaccess` の仕組みがそのまま動くので、コードの追加作業は不要
  > （`.br`/`.gz` は既に本番へアップロード済み）。
  > WAFを有効のまま行くなら `.htaccess` では解決できないため、圧縮は諦めて
  > HTML/JS 自体を削る方向（`.panel` の削減、RSCペイロードの `.txt` 198本の見直し等）になる。
  > 現状トップの HTML は非圧縮 420KB で配信されている。

  以下は実装の記録：

  本番は圧縮が**まったく効いていなかった**（トップの HTML が非圧縮 420KB で配信されていた）。
  さくらに `mod_brotli` も `mod_deflate` も無いため、**事前圧縮方式**を採用。
  - `scripts/precompress.mjs` … `out/` の html/js/css/txt/xml/svg/json（1KB以上）を
    Brotli(q11) と gzip(level 9) で二重に書き出す。`npm run build:sakura` に組み込み済み。
    実測 196ファイル・19.30MB → **br 2.45MB（-87%）** / gz 3.36MB（-83%）。トップは 420KB → **33KB**。
  - `public/.htaccess` … `mod_rewrite` で `Accept-Encoding` を見て `.br` → `.gz` → 素の順に配信。
    `AddEncoding` で Content-Encoding を、`Header merge Vary Accept-Encoding` でキャッシュ汚染対策を付与。
  - 検証（**ローカルApacheのみ。本番では上記のとおり無効**）：
    macOS 内蔵 Apache 2.4 をさくら相当の `AllowOverride`（Options 抜き）で起動して確認。
    トップ / 下層 / RSC の .txt / sitemap.xml / icon.svg / js / css で `Content-Encoding: br` と
    正しい Content-Type を確認、末尾スラッシュの301と404も維持、展開後の中身がバイト一致することも確認済み。
    woff2・ico・webp は元から圧縮済みなので対象外（素で配信される）。
  ※ GitHub Pages 側は元から Brotli 対応済みのため、`build:pages` では事前圧縮しない。
- **`.panel` の `backdrop-filter` 除去（表示速度・未着手）**：
  トップに27枚あり、PCでのスクロール負荷の主因。不透明なグラデーション背景に置き換えると軽くなるが、
  見た目が変わるため要判断。
- **コラムの追記**（2026-08-03 に基盤は実装済み・記事3本）：`src/lib/columns.ts` に足すだけで
  一覧・目次・構造化データ・sitemap・llms.txt・チャットボットまで自動で追従する。
  次に書くと効きそうな題：「ホームページ制作の見積書の読み方」「京都でWeb制作を頼むときの選び方」
  （地域名を含む記事はローカルSEOにも効く）／「AIチャットボットを自社サイトに入れるには」。
- **🤖 Web制作エージェント（本命構想）**：
  - 受託のWeb制作業務（ヒアリング→構成設計→コピー→実装→SEO/AEO/LLMO→公開）をAIで遂行するエージェント。
