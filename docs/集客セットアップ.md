## 0.7 独自ドメイン `yebisusoft.jp` をサイトに割り当てる（1章より先にやる）

**狙い**：公開URLを `https://www.yebisusoft.jp` に切り替える。
ドメインはさくらで取得済みなので、DNS の移管作業は不要です（さくら側で完結）。

> **正規URLは `https://www.yebisusoft.jp`（www あり）**です。
> コード側（`src/lib/site.ts` / `package.json` / `public/api/contact.php` / `scripts/deploy-sakura.sh`）は
> すべてこの前提に変更済みです。www なしでのアクセスは、さくら側で www ありへ転送します。

### 0.7-1 ドメインをサーバーに追加する

1. サーバーコントロールパネル（0.5 の入口）にログイン
2. 左メニューの **「ドメイン/SSL」** → **「ドメイン/SSL」**
3. 右上の **「ドメイン新規追加」**
4. さくらで取得済みのドメインの一覧に `yebisusoft.jp` が出るので **「追加」**
5. **www ありを正規にする**ので、`www.yebisusoft.jp` を追加します
6. 追加したドメインの **「設定」** で

   | 項目 | 値 | 理由 |
   | --- | --- | --- |
   | **ドメイン利用設定** | マルチドメインとして利用する | — |
   | **www.が付与されたサブドメインも利用する** | ☑ 入れる | www あり／なしの両方を同じ設定で受ける |
   | **Web公開フォルダー** | `~/www` ＋ **`/yebisusoft.jp`** | **`~/www` は指定できない**（初期ドメインが使用中で、フォルダの重複が禁止されている）。よって独自ドメイン用のフォルダを1階層掘る。`scripts/deploy-sakura.sh` の `REMOTE_DIR` もこれに合わせてある |
   | **SSLの利用** | ☑ SSLを利用する | 無料SSL（Let's Encrypt）。反映まで数十分かかることがある |
   | **HTTPS転送設定** | ☑ HTTPSに転送する | http でのアクセスを https に寄せる |
   | **www.転送設定** | **転送しない** | www なし → www ありの301は `public/.htaccess` で行う（さくら側の転送と二重にしない） |

7. www なし（`yebisusoft.jp`）は、6の「www.が付与されたサブドメインも利用する」で一緒に受けられます
   （別ドメインとして追加する必要はありません）。無料SSLの証明書も www あり／なしの両方が
   SAN に入ります。www なし → www ありの **301 は `public/.htaccess` に実装済み**です
   （`RewriteCond %{HTTP_HOST} ^yebisusoft\.jp$`）

> **⚠️ Web公開フォルダーの入力ミスに注意（2026-08-09 に実際に踏んだ）**
> 欄にドメイン名を入れる形になっているため、設定を誤ると
> `https://www.yebisusoft.jp/` が `https://www.yebisusoft.jp/yebisusoft.jp` へ301し続け、
> 全ページが404になります。**`curl -sSI -k https://www.yebisusoft.jp/`** が
> `200` を返すことを必ず確認してください。この状態だと無料SSLの所有確認
> （`/.well-known/acme-challenge/…`）も失敗するので、証明書もいつまでも発行されません。

### 0.7-2 SSL証明書を発行する

**0.7-1 と 0.7-3（デプロイ）を先に済ませてから行います。** 無料SSLは所有確認のために
`http://www.yebisusoft.jp/.well-known/acme-challenge/…` を読みに来るため、
公開フォルダが正しく、かつファイルが置かれていないと発行に失敗します。

1. ドメイン/SSL の一覧で `yebisusoft.jp` の **「独自SSL」** をクリック
2. 既存の証明書があれば **「登録解除」**（失効した証明書が残っていると更新されないことがある）
3. **「無料SSLの利用」→「無料SSLを設定する」**
4. 反映まで数十分〜数時間。次のコマンドで確認する

   ```bash
   # 有効期限が「今日より先」になっていること
   echo | openssl s_client -connect www.yebisusoft.jp:443 -servername www.yebisusoft.jp 2>/dev/null \
     | openssl x509 -noout -dates -ext subjectAltName

   curl -sS -o /dev/null -w '%{http_code}\n' https://www.yebisusoft.jp/   # 200
   curl -sSI https://yebisusoft.jp/ | head -5   # 301 で www ありへ飛べば正しい
   ```

> 発行前は証明書エラーで疎通確認が通らないため、デプロイは
> **`CURL_INSECURE=1 npm run deploy:sakura`** で証明書検証を飛ばします。
> 発行後は必ず付けずに実行すること（証明書の異常に気づけなくなるため）。

### 0.7-3 新ドメインでデプロイし直す

```bash
npm run deploy:sakura
```

ビルド時に `NEXT_PUBLIC_SITE_URL=https://www.yebisusoft.jp` が入るので、
canonical・OG画像・sitemap.xml・robots.txt・llms.txt・構造化データの絶対URLが
すべて新ドメインに変わります。**旧ドメインのままの状態で放置しないこと**（自己参照 canonical が
旧ドメインを指し続け、新ドメインがインデックスされません）。

### 0.7-4 旧ドメイン（`ebisusoft.sakura.ne.jp`）の扱い

公開フォルダが別々（旧＝`~/www`、新＝`~/www/yebisusoft.jp`）なので、
**旧ドメインには 2026-08-09 時点の古いビルドが残ったまま**になります。
中身の canonical は旧ドメインを指すため、放置すると新旧が競合します。
`npm run deploy:sakura` は新フォルダにしか転送しません。

**新ドメインの表示が確認できしだい、旧ドメインは閉鎖してください**（下記）。
急ぐ場合は、`~/www` 直下に新ドメインへ301するだけの `.htaccess` を置く方法もあります。

**新ドメインでの表示・問い合わせ送信・Search Console の登録が確認できたら、旧ドメインを閉鎖します。**
閉鎖時にやること：

- [ ] `~/www` 直下の古いビルドを削除する（新サイトは `~/www/yebisusoft.jp` にあるので影響しない）。
      あるいは `~/www/.htaccess` を「新ドメインへ301するだけ」の内容に置き換える
- [ ] `public/api/contact.php` の `ALLOWED_HOSTS` から `'ebisusoft.sakura.ne.jp'` を削除
- [ ] Search Console の旧プロパティを削除
- [ ] GA4 のデータストリームURLが新ドメインになっているか確認

## 1. お問い合わせメールを届くようにする（最優先）

**狙い**：訪問者が増えても、受け皿がなければ意味がない。ここが最初。

送信は `public/api/contact.php`（さくらの PHP）で行います。外部のフォームサービスを
使っていないので、お客様の入力内容が第三者を経由しません。

### 1-1. 差出人のメールアドレスを作る

作るのは **`no-reply@yebisusoft.jp`** です。

> なぜ必要か：差出人が自ドメインでないと、受信側で「なりすまし」と判定され
> （SPF レコードとの不一致）、自動返信メールが迷惑メールに振り分けられます。
> このアドレス宛の受信は使わないので、パスワードは何でも構いません。

> **前提**：0.7 で `yebisusoft.jp` をサーバーに追加してあること。
> 追加前はドメインの選択肢に出てきません。
> ドメインをさくらのDNSで運用している場合、SPF レコードはさくら側で自動的に設定されます
> （`ゾーン編集` に `v=spf1 a:www????.sakura.ne.jp mx ~all` 相当の TXT が入っているか確認）。

手順（0.5 のログインを済ませた状態から）。
**メニュー名は実画面で確認済み**（2026-08-03。SAKURA Web Hosting Control Panel Version 2）：

1. 左メニューの **「ユーザー/メール」** をクリック
   （公式マニュアルには「メール」と書かれているが、実際の表示は **「ユーザー/メール」**）
2. 開いたサブメニューの **「ユーザー・メールアドレス」** をクリック
   （同じく、マニュアルの「メールアドレス一覧」に相当する項目）
3. 一覧の右上にある緑色の **「新規追加」** ボタンをクリック
4. 入力する（**このアドレスは「PHPがメールを送るときの差出人」専用**。人がログインすることも、
   受信を読むこともないので、権限は最小にする）

   | セクション | 項目 | 設定する値 | 理由 |
   | --- | --- | --- | --- |
   | 基本項目 | **ユーザ名** | `no-reply` | @より前だけ |
   | 基本項目 | **ドメイン** | `yebisusoft.jp` | 独自ドメイン（初期ドメインではない） |
   | 基本項目 | ユーザの説明 | `お問い合わせフォーム 差出人` | 一覧に出るメモ。任意 |
   | 基本項目 | **パスワード** | 任意（強いもの） | 人はログインしないが、漏れると迷惑メールの踏み台にされる |
   | 基本項目 | **ユーザー権限** | **一般ユーザー**（既定） | 管理者／準管理者／Web管理者は**すべて不要**。持たせると漏洩時にドメイン設定やサイトを触られる |
   | **メール利用範囲** | 利用する | **☑ 入れる** | **必須**。これが無いとメールアドレスとして成立しない |
   | **FTP利用範囲** | 利用する | **☐ 入れない** | 転送は既存の `ebisusoft` アカウントで行う。ここに権限を与えると漏洩時にサイトを書き換えられる |
   | WebDAV利用範囲 | 利用する | **☐ 入れない** | 使わない（プランによっては表示されない） |

5. 「メール利用範囲」にチェックを入れると出る細目は**すべて既定のままでOK**
   （メール容量制限／メールの受信／転送先アドレス／拒否リスト／許可リスト／
   ウイルスチェック／迷惑メールフィルター）。
   ただし **「メールの受信」を「転送専用」にはしないこと**（転送先の指定が必須になる）。
6. **「作成する」** をクリック
7. 一覧に `no-reply@yebisusoft.jp` が並べば完了

> **運用メモ**：`no-reply@` 宛には宛先不明などのエラーメール（バウンス）が溜まります。
> 受信を使わない設計なので、容量制限を小さめ（1GB程度）にしておくか、
> 半年に一度ウェブメールから空にしてください。

> なお、この画面の左メニューは
> 「ホーム／ドメイン/SSL／**ユーザー/メール**／Webサイト・データ／サーバーステータス／
> **セキュリティ**／サーバー情報／スクリプト設定／ビジネスソリューション／メニュー一覧」
> という並びです。これが見えていれば正しい画面にいます。

作成したら `public/api/contact.php` の `MAIL_FROM` と一致しているか確認します。
通知の宛先を変える場合は同ファイルの `ADMIN_TO` を書き換えてください。

### 1-2. 送信テスト

デプロイ後、実際に <https://www.yebisusoft.jp/contact> から自分宛に送ってみます。
確認すること：

- [ ] 管理者宛（`ADMIN_TO`）に通知が届く
- [ ] **そのメールにそのまま返信すると、送信者へ返信できる**（Reply-To が効いているか）
- [ ] 送信者宛に自動返信が届く。**迷惑メールフォルダに入っていないか**も見ること
- [ ] 連続で2回送ると2回目が止まる（30秒のレート制限）
- [ ] 送信後にサンクス画面が「お問い合わせを送信しました」になる
      （「メールソフトを起動しました」と出た場合は PHP に届いていない。次項へ）

### 1-3. 動かないときの切り分け

`npm run deploy:sakura` の疎通確認に `/api/contact.php` が含まれています。

| 応答 | 意味 | 対処 |
| --- | --- | --- |
| **405** | 正常（GET は受け付けない設計） | — |
| 404 | ファイルが上がっていない | `out/api/contact.php` があるか確認して再デプロイ |
| 200 でソースが見える | PHP が実行されていない | さくらのコントロールパネルで PHP の有効状態を確認 |
| 500 | PHP の実行時エラー | コントロールパネル > エラーログ を確認 |

フォーム側は、PHP へ届かなかった場合に**メールソフトでの送信へ自動で切り替える**ので、
問い合わせが完全に失われることはありません。

## 3. GA4（Google アナリティクス）を設置する

**狙い**：どのページが問い合わせにつながっているかを知る。

1. <https://analytics.google.com> でアカウント／プロパティを作成
   - プロパティ名：エビスソフト
   - 業種：ビジネス・産業市場／レポートのタイムゾーン：日本
2. データストリームで **ウェブ** を選び、URL に `https://www.yebisusoft.jp` を登録
3. 表示される **測定 ID（`G-` で始まる）** を `.env.local` に書く

   ```bash
   # .env.local
   NEXT_PUBLIC_GA_ID=G-XXXXXXXXXX
   ```

4. デプロイする（`npm run deploy:sakura`）
5. GA4 の **リアルタイム** レポートを開いた状態で本番サイトを開き、自分が数えられることを確認

### キーイベント（コンバージョン）の設定

サイト側は次のイベントを自動で送っています。

| イベント名 | 送られるタイミング | パラメータ |
| --- | --- | --- |
| `generate_lead` | お問い合わせの送信が成功したとき | `form_id: contact` |
| `contact_tap` | 電話・メールリンクをタップしたとき | `method: phone / email`、`page_path` |

GA4 の **管理 > イベント** に上記が出てきたら（初回は反映に最大24時間）、
`generate_lead` と `contact_tap` の「キーイベントとしてマークを付ける」をオンにしてください。
これで「どのページを見た人が問い合わせたか」がレポートで追えるようになります。

> - 測定 ID を設定しないビルドでは gtag.js を**一切読み込みません**。
>   ローカル開発で自分のアクセスが混ざることはありません。
> - プレビュー（GitHub Pages）でも読み込みません。本番と二重に数えないためです。
> - プライバシーポリシー（`/privacy`）には GA4 利用を明記済みです。

## 4. さくらの WAF を無効化して圧縮を効かせる

**狙い**：表示速度。トップの転送量が **1,726KB → 約330KB** になります。
表示速度は検索順位の要因であり、離脱率にも直結します。

### 背景（なぜ今は効いていないのか）

前段の WAF（SiteGuard）が**リクエストの `Accept-Encoding` ヘッダーだけを削除**しており、
Apache に「このブラウザは Brotli を受け取れる」という情報が届きません。
そのため事前圧縮した `.br` / `.gz` が選ばれず、非圧縮のまま配信されています。
`.htaccess` 側では解決できないことを実測で確認済みです（`docs/引き継ぎ.md` 6章）。

このサイトは**完全な静的配信**で、動的処理は問い合わせ受け口の PHP 1本だけです。
その PHP は入力をメール本文にしか使わず、ヘッダーインジェクション対策・
ハニーポット・レート制限・送信元ホスト検証を実装済みなので、WAF を切っても守る対象がありません。

### 手順

1. コントロールパネルにログインする（**0.5 の入口**から。メールアドレスでログインすると
   「セキュリティ」メニュー自体が表示されません）
2. 左メニューの **「セキュリティ」** をクリック
3. **「WAF設定ドメイン」** をクリック
4. ドメイン一覧が出るので、`www.yebisusoft.jp` の行の **「設定」** をクリック
5. 「WAF設定変更」の画面で **「利用しない」** を選ぶ
6. **「保存する」** をクリック
7. 反映を待って（数分）、下記で確認する

   ```bash
   curl -sS -o /dev/null -D - -H 'Accept-Encoding: br, gzip' https://www.yebisusoft.jp/ \
     | grep -i 'content-encoding'
   ```

   `content-encoding: br` が返れば成功です。何も出なければまだ効いていません。

`npm run deploy:sakura` の最後にも同じ確認が入っており、
効いていなければ警告が出ます（デプロイ自体は成功扱い）。

> **「WAF設定ドメイン」に `www.yebisusoft.jp` が出てこない場合**
> WAF は「ドメイン設定」で登録されたドメインに対して設定します。追加したドメインが
> 一覧に出ないときは、そもそも WAF が適用されていない可能性があります。
> その場合でも `Accept-Encoding` が消えているなら、原因は WAF ではなく
> さくら側の共通のフロント（nginx）です。そのときは無理に追わず、
> 圧縮は諦めて HTML/JS 自体を削る方向に切り替えてください（7章参照）。

## 4.5 【重要】AIクローラーがさくら側でブロックされていないか確認する

**狙い**：LLMO（AI検索での引用）を潰さない。**WAFを見るついでに必ず確認すること。**

さくらは 2026年2月10日から **「ウェブサイトアクセス制御機能」** を提供しています。
コントロールパネルから、次の3種類のAIボットを**まとめて遮断できる**機能です。

| 項目 | 遮断される相手 |
| --- | --- |
| AIデータスクレイパー | 学習用に情報を抽出・取得するAIボット（GPTBot など） |
| AI検索クローラー | AI検索のために巡回するボット（OAI-SearchBot・PerplexityBot など） |
| AIアシスタント | 対話型AIがその場で閲覧しに来るアクセス（ChatGPT-User など） |

**このサイトはAIクローラーを歓迎する設計です。**
`robots.txt` で GPTBot・ClaudeBot・PerplexityBot・Google-Extended 等を明示的に許可し、
`/llms.txt` を置き、構造化データを厚くしているのは、すべて **AI検索から引用されるため**です。
ここでさくら側の遮断が有効になっていると、**サイト側の設定が何をしても届かず、
LLMO 施策が丸ごと無効になります**（しかも robots.txt は正常に見えるので気づけません）。

### 手順

1. 左メニューの **「セキュリティ」** をクリック
2. **「ウェブサイトアクセス制御」** の項目を見る
3. 上記3項目に **チェックが入っていないこと**（＝遮断していないこと）を確認する
4. 入っていたら**外して**、**「保存」** をクリック

> 公式マニュアルに初期値の記載がないため、**目視で確認する以外に方法がありません**。
> 一度確認したら、WAFの設定変更後にもう一度見てください（同じ画面の項目なので巻き込み事故が起きやすい）。

### 確認方法（実際にAIクローラーとして取得してみる）

```bash
curl -sS -o /dev/null -w '%{http_code}\n' \
  -A 'Mozilla/5.0 (compatible; GPTBot/1.0; +https://openai.com/gptbot)' \
  https://www.yebisusoft.jp/
```

`200` が返れば通っています。`403` などが返る場合は遮断されています。

## 8. ChatGPTに「京都でWeb制作を依頼したい」と聞かれて候補に挙がるようにする

**狙い**：ChatGPT・Perplexity・Google AI Overviews が「京都のWeb制作会社」を挙げるとき、
その候補リストにエビスソフトを入れる。**この章は他の章と性質が違い、大半がサイトの外の作業です。**

### 8.0 いま挙がらない理由（2026-08-13 実測）

実際に検索して確かめた結果は次の2点でした。

1. **「エビスソフト 京都 Web制作」「yebisusoft.jp」で検索しても、当サイトは1件も出てこない。**
   ＝ まだ検索エンジンの索引に入っていない。この状態では、AIがどれだけ探しても見つけようがない。
2. **「京都 Web制作会社 おすすめ」で上位に出るのは、ほぼ全部が“まとめ記事”**
   （Web幹事、PRONIアイミツ、優良WEB、STUDIO の地域記事、Baseconnect、イケサイなど）。
   AIはこの手の記事を読み込んで会社名を並べているだけで、各社のサイトを1件ずつ回っているわけではない。

つまり候補に挙がる条件は2つあり、**効き方は (A) のほうが圧倒的に大きい**です。

| | 条件 | やること | 誰が |
| --- | --- | --- | --- |
| **A** | まとめ記事・企業データベースに社名が載っている | 8.2 の掲載サイトへ登録 | 依頼主（手作業） |
| **B** | 自社サイトが索引に入り、地域＋業種の質問で取り出せる | 8.1（索引登録）＋ 8.5（実装済み） | 8.1 は手作業 |

**サイト側をどれだけ作り込んでも、A をやらなければ候補には入りません。**
逆に A だけでも名前は挙がりますが、そこから先（本当に頼むか）で B が効きます。

### 8.1 最優先：Bing Webmaster Tools に登録する

**ChatGPT の Web 検索は Bing の索引を使っています。** Google Search Console（2章）とは別物で、
**こちらに登録しないと ChatGPT からは事実上見えません。** 2章より優先度が高い作業です。

1. <https://www.bing.com/webmasters> にアクセスし、Microsoft アカウントでサインイン
2. **所有権の確認**（2026-08-13 に **XMLファイル方式**で対応済み）。
   Bing が配布した `BingSiteAuth.xml` を `public/` に置いてデプロイしてあるので、
   <https://www.yebisusoft.jp/BingSiteAuth.xml> が 200 で返ります。
   Bing の画面で **「確認」** を押すだけで所有権が通ります。
   - ⚠️ **`public/BingSiteAuth.xml` は消さないこと。** 消すと所有権が外れます
   - 別の方法を使う場合：「Google Search Console からインポート」（2章が済んでいれば一気に終わる）、
     または HTMLメタタグ方式（`layout.tsx` に入れる形になるので実装側に渡してください）
3. **サイトマップを送信**：`https://www.yebisusoft.jp/sitemap.xml`
4. 左メニューの **「URL 検査」→「インデックス登録をリクエスト」** で、
   トップ・`/web`・`/request`・`/columns/kyoto-web-seisaku-irai` の4本を手動で送る
5. 1〜2週間後、`site:yebisusoft.jp` を Bing で検索して登録ページ数を確認する

> Bing は Google に比べて登録が遅いので、**新しいページを作ったら毎回 URL 検査から手動送信**するのが確実です。
