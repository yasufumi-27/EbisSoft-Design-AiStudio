# サイト品質点検（2026-09-17）

## 結論

技術的な検索設定と基本品質は整っているが、「すべて問題なし」とは言えない。優先課題はモバイルの初期表示速度と、実績・短縮率を検証できる公開資料の充実。

## Lighthouse 初回実測

対象は GitHub Pages のコミット `7e395ca`。Lighthouse 13.4.1、ローカルChrome、デフォルトのモバイル模擬通信・CPU設定。PCはdesktopプリセット。各行1回のラボ計測で、実ユーザーのCore Web Vitalsや検索順位の評価ではない。

|AI|スマホ|77|100|100|66|5.3秒|30ms|0|

SEO 66はプレビューの `noindex` が原因。本番用出力では解除される。修正後の本番用ローカル `/contact` は Accessibility / Best Practices / SEO が100。このローカル値を、本番の通信速度やサーバー性能の点数として扱わない。

### 実測からの優先改善

1. 常駐クロマのPNGは1254×1254・581,496 bytes。スマホの実表示は約44×44pxで、Lighthouseは大部分が過剰な転送と指摘。透過・デザインを維持して表示サイズに適した配信用画像を用意することが最優先。
2. 通常のキャラクター画像も表示用途ごとのサイズ・形式を用意する。静的書き出しで画像最適化を無効化しているため、自動縮小はされない。
3. LCP、フォント・CSSの読み込み順を確認。トップのLCP対象は見出し。画像の軽量化だけで全遅延が解決すると断定しない。
4. GitHub Pagesのキャッシュ指摘と、さくら本番のヘッダーを区別して再測定する。

アニメーションをすべて削除する必要があるという結果ではない。今回のTBTは0〜30ms、CLSは0で、大きな課題は初期表示。INPの実ユーザー値・バッテリー負荷・長時間スクロールの性能はこの計測では判断しない。

## この点検で修正したもの

- お問い合わせ文字数カウンターのコントラスト・サイズ。
- 独立したキャラクター案内の見出し順序。
- ロゴの表示ラベルと読み上げ名の整合性。
- FAQ、コラム、強み紹介などの「現在もLighthouse 100点」という断定。今回の実測と一致しないため、計測・改善を行う説明に修正。
- 画面幅ごとの改行。320pxでの業種見出し末尾の「こと」や「の」の孤立、歯科デモの狭い段組み、アパレル見出しの文字サイズ・余白、業種デモの語尾だけの行を調整。

## E-E-A-T

確認済みの土台：代表者・著者名、会社情報への導線、所在地・連絡先、公開日・編集日、記事署名、本文と対応した構造化データ。デモは架空の事業・顧客の声である旨を表示し、検索除外としている。

補強が必要な点：

- 「約1/3」「AIが約7割」「最短5日」などの数値には、対象期間・案件数・作業範囲・比較条件・人による確認工程を公開資料として添える。今回、根拠となる個別案件記録の監査は行っていない。根拠を用意できない値は一般的な保証のように表示しない。
- 公開可能な実案件について、依頼内容・担当範囲・課題・改善結果を示す。業種デモは技術の紹介にはなるが、顧客の導入実績を示す証拠の代わりにはならない。
- 第三者が確認できる実在の事業者プロフィール・掲載情報へのリンクを充実させる。`sameAs`は現在空。SNSを作ること自体が必須という意味ではない。
- AIキャラクターによる案内と、実際の責任者・執筆者を引き続き区別する。

E-E-A-Tはサイトに付与される公式の数値スコアでも、単一のランキング要因でもない。掲載情報を検証でき、読者に役立つかが中心。構造化データや著者欄だけで権威性を保証するものではない。
